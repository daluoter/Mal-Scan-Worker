## 1. 先讓 demo 可持續運作

本輪核心流程已驗證；以下持續維護條件繼續追蹤，可與下一階段靜態品質工作並行。
這些狀態不改變本節的完整出口條件，也不需要另起一套架構。

- 在已部署 v2 跑完小型巢狀 ZIP／7z、外內層不同密碼、錯誤後補交正確密碼；檢查 artifact tree、部分報告、完成時間與累計預算，確保完成階段沒有重跑。
- 用正式 v2 流程驗證 20,000,000-byte 原檔、超限拒絕、大小與 SHA256 一致；和舊 upload-only PoC 分開保存證據。
- 驗證同 ticket／dispatch 重放、瀏覽器刷新、Cloud Shell 斷線及結果不確定情況；確認不產生未經授權的額外 execution，已有成果可核對。
- 驗證 R2 到期物件清理、DO 狀態清理、實際保留時間，以及日／月 execution 限額；resume 與不確定派送也計入用量。
- 建立有紀錄的病毒碼更新流程：官方簽章驗證、掃描控制樣本、產生新映像 digest、更新 Job、保留可回退版本。先驗證手動流程，再選擇符合成本目標的排程；目前尚無自動每日更新。
- 保存 Cloud Build、Artifact Registry、Cloud Run、R2、Secret Manager 與 Logging 的實際用量。預算告警用來提醒，不能當成費用硬上限。
- 使用新加入的 CI 持續執行共用核心、前端、控制層與 dispatcher 測試；定期審查仍有 advisory 的開發／部署工具，採相容升級並重跑驗證。

**出口條件：** 以上案例有對應的版本、輸入、預期結果、實際報告與清理結果；已能說明 demo 每次工作及每月維護的實際成本範圍。

## 2. 讓靜態結果更值得信任

2026-10-16 第一批已實作：18 案例的固定品質 corpus、artifact-scoped 子檔案證據、
同 root 重複內容的受驗證引用、YARA 規則來源清單與工具版本呈現。
同時修正重複內容排列影響分數、父報告風險欄位不同步、去混淆提早截斷仍顯示正常等問題。
範圍與執行方式見[品質基準](static-quality.md)；這是 P1 基礎批次，不代表所有格式或偵測品質已完整驗收。

2026-10-17 第二批新增 3 個 PE、9 個 Office／PDF、2 個 Java 正常／指標案例。
規則集 `1.1.0` 將 `network_iocs` 留作零風險 context，JSP 需要附近的 request＋程序執行字串；
`msrs-v1.1` 保留原始 IOC 證據且不單獨加分。正常 PE 的無 overlay 解析與 OOXML／PDF 失敗範圍也同步修正。
32／32 原生案例及 worker 717、backend 203、frontend 34 項測試通過，舊 v1 仍保留歷史輸入與舊預期。
這些合成對照縮小已量測的誤報，沒有建立真實世界偵測率結論，也沒有新增文件密碼解密能力。

本批對應以下三項基礎交付，後續持續擴充樣本與覆蓋：

1. 版本化品質 corpus：正常、命中與失敗／受限樣本分組，記錄 fixture 身分、預期 stage 狀態與證據，形成誤報及品質回退基準。
2. artifact 證據完整性：核對 coverage、重複內容引用及 direct／inherited risk；工具失敗、未支援與零命中維持不同結論。
3. 規則來源與版本：YARA 規則的來源、授權、版本及雜湊可追溯，工具版本與 ClamAV 病毒庫版本／日期分開呈現。

- 將正常檔、EICAR、各格式異常檔與已知特徵樣本整理成版本化 corpus；以 coverage、誤報／漏報、時間與記憶體觀察品質，不能只檢查程序退出成功。
- 完善自架重複內容節點的證據引用：保留每個出現位置，讓省略重複派送的節點可追溯到真正完成的分析；引用失敗維持 unknown／partial。
- 建立 YARA 規則來源、授權、更新、測試與停用機制。現有 5 檔／15 條是起點，先擴充高價值規則並驗證誤報，不以規則數量宣稱偵測品質。
- 將工具版本、病毒庫版本／日期、規則雜湊及其來源分開呈現；讓使用者能理解本次實際用到的內容與缺漏。
- 持續核對 direct／inherited risk、IOC 出處與 offset、原始／衍生內容關係，避免將零命中、工具失敗和不支援格式混在同一結論。

**出口條件：** 每項新增偵測都有正常／命中／失敗對照案例；報告能指出證據來源及未分析內容；既有 corpus 沒有未解釋的品質回退。

## 3. 依常見附件擴充格式能力

以[支援矩陣](analysis-support.md)為準，先填常見使用情境的缺口：

第二批先建立 PE／OOXML／PDF 的正常、指標及損壞／受限對照，
其中加密 PDF 與無可解析 VBA 來源如實為 partial；不是將第 3 項的密碼／附件能力全部完成。
F-01 PDF 密碼恢復程式／本機驗證完成，F-08 另追蹤正式部署。接續順序為 F-02 Office 密碼、
F-03 PDF 附件／Office 嵌入物件，再依實測擴充 Q-06 格式品質與 IOC／去混淆雜訊；
F-05 PE／LNK 等項目保留各自狀態與驗收條件。維護待辦與這些功能並行。

1. 壓縮檔：ZIP／7z／RAR 的加密變種、損壞與同名 entries、深層遞迴及外部解壓器相容性。
2. Office／PDF：使用者提供密碼的解密、PDF 附件提取、OLE／OOXML 嵌入內容與來源證據；支援後同步接上既有 checkpoint／預算／密碼恢復契約。
3. PE／LNK／scripts：資源、overlay、巨集／腳本去混淆與衍生檔的深度分析，保留可信度及解析限制。
4. 郵件、ELF／Mach-O、ISO、APK：依實際需求逐格式排程，不先宣告整類格式完整支援。

密碼功能以使用者提供密碼解密為範圍；加入任何格式前，先定義其 extractor、資源邊界、報告證據及可重現驗收樣本。

**出口條件：** 每個宣告支援的格式／加密方式均有成功、錯誤密碼、不支援、損壞及資源超限的案例，並同步更新矩陣與 UI。

## 4. 量測後改善效能與介面

首筆 demo 的基準是建立 execution 到完成 238.075 秒，其中分析 29.331 秒，資源就緒到 `Started` 165.069 秒。這是單次觀察，尚未確定平台內部原因，也不是 latency SLO。

- 加入可核對的上傳、派送接受、容器啟動、第一個 stage、報告發布及完成時間，區分 cold／後續執行，先累積少量有用樣本。
- 將目前統一的「排隊」細分為可由證據支持的準備／分析／保存狀態；結果不確定仍保留明確說明，不顯示虛構進度百分比。
- 分別量測 Python import、ClamAV 資料庫載入、YARA compile、R2 checkpoint／report 發布及瀏覽器 polling；只對主要瓶頸修改，保留恢復與完整性保證。
- 針對每項優化比較相同輸入的前後耗時、記憶體與費用。雲端常駐 worker、服務化引擎等執行方式需另行成本評估；不以增加資源直接取代量測。
- 報告優先呈現摘要、未完成原因、來源檔案樹、證據與版本資訊；檢查大型樹、手機畫面及下載 JSON 的可用性。

**出口條件：** 有可比較的前後數據，介面能解釋等待，既有恢復／安全與分析品質驗收仍通過。

## 5. 自架動態分析實機驗收

此階段依賴部署者提供可用 CAPE host、分析 guest／snapshot 與隔離網路；不阻擋共用靜態核心的發展。已有啟用腳本，尚未完成真實 guest 驗收。

- 驗證既有伺服器執行啟用腳本後，preflight、獨立 sandbox worker、指定 guest 與實際 detonation 都正常。
- 在真實 CAPE 上驗證 task ID 保存、worker 重啟後繼續 polling、不確定提交的人工核對與 provider 失敗呈現，確認沒有盲目重送或 mock fallback。
- 驗證 process／file／registry／network、截圖／PCAP 等可取得產物與靜態報告的來源關係、下載權限與完整度。
- 再依驗收結果安排多 task 聚合、動態掉落檔重新送靜態核心及適用 artifact／guest policy。

**出口條件：** 乾淨重啟後，部署者可用文件化的一個命令啟用已備妥的沙箱；同一工作可閱讀靜態與真實動態結果，失敗及未知狀態保留原意。
